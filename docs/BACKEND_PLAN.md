# Temporary location links: proposed backend contract

Design record, November 16, 2026. **Not implemented, hosted, deployed, or tested.** This document does not establish a service, uptime promise, emergency monitoring, or an affiliation. All endpoint paths below are a proposed contract, not working URLs. A future recipient would use an ordinary supported browser without installing Safe Bridge or opening an account. No real location, recipient, account, or hosted resource was used to prepare this plan.

## Purpose and consent

Offer an optional, time-limited link to the sender's latest available location for a person the sender chooses. It must not be described as rescue, emergency dispatch, guaranteed continuous tracking, or protection from an abusive person. Device and account monitoring, share messages, browser history, notifications, OS location indicators, and the link itself can expose use. Changing access can increase danger; a trained advocate can help someone consider options. The app must never silently enable sharing on installation, calculator entry, emergency-dialer use, or a resource-link visit.

Before each session, a short paged disclosure explains who could see the position, precision, duration, notification visibility, interruption/expiry behavior, and stopping limits. The sender chooses a duration, then explicitly starts and separately opens Android's share sheet. No contact permission or automatic sending is needed. Sharing a link is not evidence that a recipient received, opened, or is watching it. The recipient page does not request the recipient's location.

Proposed initial constants, to be validated with survivor-led review and field tests: default duration 15 minutes; choices 15/30/60 minutes; hard maximum 60 minutes; target update and recipient poll intervals 15 seconds; recent-point threshold 30 seconds; upload lease 90 seconds. None is a reliability guarantee. A fresh accepted position renews the lease only up to the immutable hard expiry. An old point or heartbeat must not keep a session alive. After a lease lapse, a new session and new link require the sender's explicit action.

## Trust boundaries and credentials

Use three independent cryptographically random 256-bit secrets: `writeToken`, `revokeToken`, and `readToken`. Generate with the platform CSPRNG. No token is derived from another token, phone number, password, device ID, timestamp, or coordinate. Use a separate random 128-bit-or-larger session ID and a server generation ID. Knowledge of a session ID alone grants no access.

- The Android sender retains the write and revocation credentials. Neither goes into the recipient link, share sheet, screenshots, analytics, logs, crash reports, or OS notification text.
- The recipient link contains only the session ID/generation and read credential. Possession is authorization to read while valid; a forwarded link gives its recipient the same access. It cannot update positions, extend expiry, or revoke the session.
- The server stores a keyed HMAC verifier of each token with separate scope/domain labels, using a protected service key. Compare verifiers in constant time and authorize the required scope on every endpoint. Do not use a self-contained token that remains valid after server revocation.
- The sender stores minimal management state encrypted with an Android Keystore-protected key in private, backup-excluded storage: session ID/generation, hard expiry, local stopped flag, and pending revocation credential. Do not persist coordinates, a route, recipients, or upload queues. Keystore/storage access can still be compromised on a monitored device; no concealment promise is made. Lost management credentials cannot be recovered by an account or support agent.

The proposed share form is `https://<approved-origin>/view#s=<generation-and-session>&r=<readToken>`. The fragment prevents automatic HTTP transmission of the read secret on the initial document request; first-party JavaScript reads it and places it only in an Authorization header for same-origin API calls. It is still exposed to the browser, link recipients, extensions, clipboard/history/sync, screenshots, messaging providers, and any script running on the page. It is not anonymous or end-to-end encrypted. The hosting/service operator processes plaintext coordinates; disclose that fact. Any later end-to-end encryption design requires independent protocol review and must not be advertised before implementation.

Capability-URL exposure and revocation limits are explained by [W3C's capability-URL guidance](https://www.w3.org/TR/capability-urls/). HTTPS and per-endpoint authorization follow [OWASP REST Security guidance](https://cheatsheetseries.owasp.org/cheatsheets/REST_Security_Cheat_Sheet.html).

## Proposed API and state

Only HTTPS, strict certificate validation, and a maintained TLS configuration. Reject cleartext, cross-origin redirects, arbitrary callback URLs, tokens in query strings, and unsupported methods/content types. Tokens and coordinates never appear in endpoint paths. API paths include only a random session identifier; logs must record route templates instead of full paths. The client supplies an idempotency key for creation and each update; keys are random and log-redacted.

| Method and proposed path | Authorization | Behavior |
| --- | --- | --- |
| `POST /v1/shares` | Newly generated write credential in Authorization; independent read/revoke credentials in the encrypted JSON request | Create a session with fixed duration and generation. Return ID, server time, hard expiry, and initial lease. Idempotent retries with the same creation key return the same session and never reset its expiry. No coordinates required at creation. |
| `PUT /v1/shares/{id}/latest` | Write credential | Atomically replace the single point if the session is active, within hard expiry and lease, and sequence is newer. Return server receipt time and lease deadline. Reject expired/revoked/lapsed sessions; never recreate one. |
| `GET /v1/shares/{id}/latest` | Read credential | Return authenticated state, server time, deadlines, point age and accuracy, and at most one point. No point for ended/expired/revoked state. No history, other-session discovery, or writer information. |
| `GET /v1/shares/{id}/status` | Write or revoke credential | Let the sender resolve an uncertain acknowledgement without retrieving coordinates. Return session state and deadlines. |
| `DELETE /v1/shares/{id}` | Revoke credential | Atomically mark stopped, delete the point, and reject all future updates/reads of location. Idempotent acknowledgement means revocation committed at the authoritative store. |

The creation body is size-limited and contains only duration, read/revoke credentials, and the idempotency key; the server never reflects credentials in error messages. Creation-response loss must be tested: the sender retains its credentials before the request and retries only with the same creation key. If it cannot establish a session, it never produces a recipient link and attempts revocation when able. Creation idempotency records live no longer than the session's metadata retention.

An update contains latitude, longitude, horizontal accuracy in meters, a monotonically increasing sequence, and claimed sample age. Validate finite numeric values/ranges, a strict small body limit, and allowed fields; reject old/replayed sequences. The Android sender checks its fix's monotonic elapsed age and sends only a newly obtained fix, never a restored last-known point. Device-reported age/accuracy are not proof of actual position. Server receipt time is authoritative for server deadlines; clearly distinguish it from the device's claimed capture time. A coarse permission produces approximate coordinates with an accuracy label, never a claim of precision.

Use fixed response schemas: invalid credentials return the same generic response as an unknown session, without a lookup oracle. A valid retained credential may see `stopped`, `expired`, `interrupted`, or `waiting_for_fix`. Status and error bodies contain no coordinates. Do not infer that a sender is safe or unsafe from any state.

## Revocation, expiry, races and retention

One strongly consistent authoritative state handles all operations. Do not serve reads from lagging replicas. In a transaction or equivalent atomic script, check token scope, stopped state, hard expiry, lease, and sequence before replacing a point. Revocation and expiry are terminal: an update queued before Stop but received afterward cannot restore the point. A later session uses fresh identifiers and all-new tokens. Stop completion wins over all later writes. Requests authorized before the revocation transaction can still arrive at a recipient afterward; network bytes and already displayed/copied coordinates cannot be recalled.

Store only current coordinates, never a route/history. Prefer an isolated ephemeral store with persistence, command logging, snapshots, backups, swap and crash dumps disabled for location payloads. Provider/runtime memory and infrastructure access remain a trust boundary. A store restart or loss ends sessions as unavailable; no automatic client replay/re-creation. Bind sessions to a server-store generation so an old creation retry cannot resurrect a lost session after restart. Do not enable automated failover to replicas until revocation consistency is demonstrated. Availability loss must fail closed.

A position expires at `min(hardExpiry, lastAcceptedFreshFix + 90s)`; its storage TTL matches that deadline. Hard expiry is immutable and evaluated on every read/write with server time, regardless of cleanup worker timing. Lease lapse deletes the point and records `interrupted`; hard expiry records `expired`; an authenticated explicit Stop records `stopped`. Keep only token verifiers, random IDs, terminal reason, and deadlines as a coordinate-free tombstone until 24 hours after hard expiry, then delete them. Never extend a point's lifetime because it was viewed. A cleanup worker runs at least once per minute to purge ended points and expired tombstones, but authorization never depends on that worker. Verify that the selected infrastructure actually enforces these bounds; a plan is not evidence of deletion.

No coordinates, tokens, Authorization headers, full capability URLs, session IDs, names, or raw IP addresses in application, edge, reverse-proxy, database, trace, error, crash or support logs. Disable request/response-body capture and third-party analytics. Retain only coarse aggregate health/error counts without session dimensions. Rate-limit creation/reads/writes and cap active sessions to resist abuse; any short-lived network-abuse key must be a rotating keyed digest with a documented maximum 15-minute lifetime and no coordinate association. The infrastructure necessarily sees connecting network addresses in transit; provider retention settings and contracts require verification before claiming anything about their logs. Reject new sessions at capacity, rather than silently weakening expiry/revocation. Do not deploy until a provider can support the documented retention policy.

## Sender Stop and Android lifecycle

Start location sharing only from a visible activity after explicit consent and runtime location permission. Declare the `location` foreground-service type and required foreground-service/location permissions; accept approximate location without pressure to enable precise location. Avoid background-location permission in the initial design. Request notification permission in context. As a product safety choice, require an enabled notification channel before starting; if permission/channel visibility is removed while detected, stop collecting and attempt remote revocation.

Use a clear ongoing foreground-service notification with session expiry and a Stop action; no coordinates or read link on the lock screen. Sharing is discoverable through Android settings, location indicators, notifications and Active apps. Calculator mode must not conceal, falsify or suppress these indicators. Back/Close must not misleadingly imply Stop: present the actual sharing state, and keep Stop immediately accessible from the app and notification. No boot auto-start, sticky restart, covert location collection, silent resume, battery-optimization bypass, or notification workarounds.

In-app/notification Stop first durably sets `locallyStopped`, invalidates the upload generation, unregisters location callbacks, clears in-memory fixes/queued uploads, and stops foreground collection. Then it attempts authenticated server revocation. The UI must distinguish:

- **Stopped and link revoked:** the server acknowledged its terminal transaction.
- **Stopped on this phone; link revocation pending:** offline, timeout, or acknowledgement lost. No more fixes are collected or uploaded. The last server-held point may remain accessible until the lease/hard deadline. Retry only revocation with bounded backoff while allowed, never location uploads. Check status before declaring success.

Do not erase the pending revocation credential before acknowledgement or confirmed expiry. After reinstall, data clear, or credential loss, automatic expiry still limits access but immediate remote Stop may be unavailable. Android force-stop/Active apps Stop can terminate the process without a callback: no client can promise immediate server revocation in that case. The short lease bounds server availability after the last accepted fix, while recipients may already have copies. Do not schedule anything to restart sharing after a user stop. Reopening requires a fresh explicit start; resolve any pending revocation first.

Android requires an FGS notification, but notification permission denial can hide it from the drawer while Active apps still shows the service. Therefore notification visibility is a product gate, not an OS guarantee. Android background-start restrictions, permissions, battery settings, OEM behavior, process death, reboot, disabled GPS, network failure and the user can interrupt updates. [Android notification permission](https://developer.android.com/develop/ui/compose/notifications/notification-permission), [location FGS requirements](https://developer.android.com/about/versions/14/changes/fgs-types-required), [background-start restrictions](https://developer.android.com/develop/background-work/services/fgs/restrictions-bg-start), and [Active apps Stop behavior](https://developer.android.com/develop/background-work/services/fgs/handle-user-stopping) are the primary platform references checked for this design.

## Recipient browser behavior

Self-host a minimal first-party viewer and assets. No account, installation, geolocation prompt, cookies, ads, trackers, remote fonts, service worker, third-party JavaScript, map tiles, geocoding, or embedded maps by default. Use in-memory read credentials; no localStorage/sessionStorage/IndexedDB. Poll only while the page is visible, at the documented interval with bounded retries; on visibility restoration, revalidate before showing a point. Offer an accessible manual Refresh control.

Show receipt time, elapsed age, accuracy, deadline and a textual state. Say “Latest position received … ago,” rather than imply uninterrupted live observation. At more than 30 seconds without a fresh accepted point, mark **stale**; do not use a moving animation or “live” badge. On Stop, hard expiry or lease lapse, clear coordinates from DOM and memory and show the reason returned by the server. On a failed fetch, immediately mark connection lost; clear the displayed point after at most 30 seconds without successful revalidation. With no connection, the viewer cannot know whether the sender stopped. It must not claim “stopped” or “still sharing” from a cached response.

Serve viewer and API with `Cache-Control: no-store`, `Referrer-Policy: no-referrer`, strict Content-Security-Policy (self-only scripts/connect, no frames), `frame-ancestors 'none'`, `X-Content-Type-Options: nosniff` and restrictive Permissions-Policy including disabled geolocation. No public search indexing or preview coordinates. Do not encode sensitive data in metadata, page titles, Open Graph cards, error pages, favicon URLs or analytics. Bearer header access is same-origin; no wildcard CORS. No cookie authentication to invite CSRF. Output text safely and test CSP/XSS defenses. Browser history, back/forward caches, extensions and screenshots remain outside complete control; clear on pagehide and revalidate on pageshow, without claiming guaranteed browser erasure. [W3C Referrer Policy](https://www.w3.org/TR/referrer-policy/) documents outgoing referrer control.

An optional “Open map” action is a separate informed choice. It names the provider and explains that the external provider can receive coordinates and network/device information and may retain records. Only then navigate with `noopener noreferrer`; never send the read token or session ID, and never prefetch. No third-party request or tile loads before the choice. Avoid selecting a provider until its current privacy/licensing/availability has been reviewed. Anyone with the link can copy or forward it; expiry/revocation prevents future authorized reads but cannot recall copies, screenshots, messages, or coordinates already received.

## Independent verification and ship gate

Before any live implementation is offered, reviewers other than its author must exercise the actual service, Android app and receiver against an independent model of the contract. Test only consenting testers and synthetic locations; never use a real emergency or a vulnerable person's movement as a test fixture.

1. Scope/auth tests: read token cannot write/revoke/extend; write token cannot read unless explicitly authorized by the contract; wrong-session tokens, missing tokens and enumeration fail; random generation and constant-time comparison reviewed; logs contain no seeded canary tokens/coordinates/IDs.
2. State/race tests with a controlled server clock: queued/reordered/retried updates versus Stop; duplicate Stop; lost create/update/Stop responses; old generation/restart; future/old/NaN/oversized points; lease boundary and hard expiry; stalled cleanup and replica delay; no revival after terminal state. Assert exact maximum retention and all infrastructure copies, not just API invisibility.
3. Network/browser tests: offline at start and Stop, packet loss and delayed acknowledgements, reconnection, server unavailable, rate limits, caches and conditional requests, tab sleep, back/forward restore, stale-point clearing, link previews, referrer/header leakage, CSP/XSS, no third-party traffic before map choice, screen reader/keyboard/large-text/mobile layouts. Confirm recipients need no installed app/account.
4. Android matrix: min supported API through current Android versions and representative OEMs, permission denial/approximate/one-time/revocation, notification permission/channel changes, visible start versus background attempt, lock screen, Doze, battery saver, rotation/split screen, task removal, process death, reboot, airplane mode, GPS off, Active apps Stop and force-stop. Verify no silent restart and no upload after local Stop. Confirm actual notification/Stop controls and measure update/lease delays.
5. Adversarial privacy/abuse review: stolen/forwarded link, sender phone compromised, malicious recipient screenshots, provider access/legal disclosure, session flooding, credential theft, supply-chain/XSS risk, and safe failure during deployment rollback/store loss. Assess minor/guardian consent and jurisdiction-specific legal duties with qualified reviewers; do not infer these from a generic app age label.

Ship only after survivor-led safety review, child-safety/privacy/legal review, independent security assessment, verified retention/logging configuration, incident response and abuse process, an accountable operator and maintenance budget, accessible device testing, and clear truthful sender/receiver copy. Hosting/domain/provider selection, production keys, infrastructure, capacity/SLO evidence and operational ownership remain unresolved. No public availability or reliability claim is justified by this document. The existing prototype must keep location sharing clearly unavailable until a real backend and device/receiver behavior satisfy this gate. No hosting account, backend deployment, public release, live service test or real-device test was performed for this plan.
