# Independent security review: durable lab 0.9

November 16, 2026. This review covers the separate `safe-bridge-durable-lab` protocol-3 implementation and independently owned tests in this directory. Earlier artifacts were not modified. No deployment, real coordinate collection, recipient contact or emergency call occurred.

## Executed evidence

The final independent Node command, `node --test live/security-tests/*.test.mjs`, passed **99/99 cases**: 28 general HTTP, 9 actual prepared-production-mode TLS, 11 SQLite/integrity/limitation cases, 14 child-process crash/HTTP cases, 3 actual private install CLI cases, 6 actual offline prepared-recovery CLI cases, 21 current recipient regressions in the historically named V2 file, and 7 durable recipient integration cases.

The actual pure-Java coordinator passed **206 independent assertions**. The policy suite passed **94 checks**, executing pure retry/end-choice/interruption/reset-only helpers and explicitly source-based Android integration checks. Commands and per-file boundaries are in [README.md](README.md). The parent's full run includes these suites; their totals are not additional tests.

The 28 general HTTP cases deliberately use an anonymous ephemeral development fixture for protocol boundary regressions. They do not establish durable production behavior. The TLS, crash and new recipient cases use prepared grants and actual durable SQLite. TLS tests use disposable private temporary certificate/key material with explicit Node-client trust; default trust and hostname mismatch reject. They do not exercise Android TLS or validate production operations.

## Durable state and actual crash checks

The store persists encrypted control state: stable generation and server keys, scoped credential verifiers, session ID/lifetime, last accepted sequence, terminal state and prepared-slot epoch/binding. It excludes coordinates, accuracy, point/sample metadata, recipients and location history. Independently decoding AES-GCM records with a synthetic test key confirms their fields. Tests also accept a real synthetic point through HTTP, kill the separate server process, inspect reopened persistent state, check file canaries and confirm no server point can be recovered by an old or new recipient tab.

The crash fixture intercepts a normal handler's final response only after it has reached acknowledgement, signals the test privately and withholds that response. SIGKILL then destroys process memory. A new child opens the same authenticated SQLite state:

- Lost creation acknowledgement resolves to exactly the original ID and one allocation.
- Lost PUT acknowledgement preserves the accepted sequence. Old sequences cannot rehydrate a point; a fresh higher sequence resumes the same link.
- Stop and own-slot reset survive loss of their acknowledgement and process death. Their epoch advances and slot release persist.
- A kill while a creation body is incomplete allocates nothing. A reset committed before that body finishes makes its old ticket/epoch fail without creating an empty orphan.
- A second child cannot own the same database. SIGKILL releases the OS ownership, allowing the next process to open it.
- A positive selected expiry remains exact across restart. Until Stop remains nonterminal after seven synthetic days of downtime. Recovered nonterminal sessions are paused with no point, not silently ended or automatically collecting.

SQLite uses DELETE journaling, FULL synchronous mode and exclusive ownership. AES-GCM AAD binds each record's bucket and ID. An independently encrypted manifest authenticates the current sorted record set and revision. Tests reject wrong keys, missing state/records, injected schema objects, modified ciphertext/tags, cross-record swaps and old valid ciphertext replay for one record. Initialization does not overwrite existing state; opening missing/corrupt state does not generate a replacement identity.

These are actual process-crash checks around commit/acknowledgement boundaries. They do not simulate physical power loss, torn sectors, disk-full errors, kernel failure or an fsync implementation that lies. No stale-WAL replay experiment occurred; this implementation explicitly selects DELETE journaling. OS/filesystem and backup recovery remain operational concerns.

## Prepared access and replay boundaries

Actual private CLI tests provision a sender bundle and verifier-only configuration, initialize durable state, create/Stop a session, add a second grant and install it offline. The generation, old Stop and first slot's advanced epoch remain unchanged. Installing while the server owns the database, reinitializing, removing/replacing existing grants and exceeding sealed capacity reject. Public config does not provide an enrollment path; a random/unprepared sender cannot obtain admission or occupy a slot.

The final design uses a durable per-slot epoch and one-active-session binding rather than a permanent 4,096-start ledger or a shared prepared nonce pool. This avoids a lifetime start limit and prevents one authorized slot's repeated starts/Stops from exhausting another reserved sender's nonce capacity. Ordinary global/network rate limits and denial of service still affect availability.

Client and server jointly enforce the important acknowledgement boundary:

1. Before an admission reply has been durably saved, no creation POST may be dispatched. A lost admission reply can therefore be retried as a fresh request without claiming an earlier session exists.
2. The acknowledged ticket and epoch are durably journaled before creation. A lost creation reply remains uncertain and retains its exact key, credentials, chosen end and integer epoch.
3. Ticket/permit refresh uses that saved epoch. The client also rejects an issuance reply that changes a non-null epoch. A reset, Stop or expiry durably advances the slot epoch; an old uncertain intent cannot silently cross it after terminal-cache eviction.
4. A new explicit intent may obtain the current epoch and a new ID. This does not revive the old link. Possession of a valid long-lived grant is authority to create new sharing in that slot; it is not proof the same human still controls it.

HTTP/TLS cases verify grant/read/write/revoke separation, cross-slot reset denial, generation binding for admission/reset, ticket key/epoch/expiry, no secret-bearing recipient response, strict body/range/media/freshness limits, hostile Host/Origin/query rejection, privacy headers and priority for a first authenticated Stop/reset. Neither the prepared grant nor the bound ticket is a recipient credential.

## Offline compromise recovery

Six independent cases run the actual offline operator CLI to disable, rotate and enable a grant. Old setup tokens lose admission/reset authority; default disable/rotation preserves the current session ID, existing management/read capabilities, sequence and immutable end. Explicit `--end-current` ends the selected current session. A disabled slot remains disabled after secret rotation until explicit enable. Stale configuration cannot restore the old verifier or enabled policy; a private verifier-only v2 export supports a consistent add-only view. Live-database lock, wrong slot, duplicate/unknown flags and no-clobber output failures are checked without state mutation or secret output.

A new independent fixture injects a precise failure into the actual CLI: a test-only Node preload stops execution at its SQLite write-transaction boundary, after the new bundle and authenticated receipt have been published and synced. The parent SIGKILLs that child and reopens the actual database. It still contains the original verifier/epoch/session while the new private files exist. This establishes that output publication alone is not activation.

Normal `--recover-rotation` validates the private same-slot bundle and HMAC-authenticated compare-and-swap receipt, bound to generation, origin, old verifier/epoch, new verifier, disabled policy and the original active ID for a destructive choice. It applies once. A later replay cannot repeat Stop against a newly created session. The test also prepares a destructive rotation while the slot is empty, lets a new session start without changing its epoch, and verifies recovery refuses to end that unreviewed ID. Tampering with the receipt or mismatching the bundle fails. This test injects a pre-transaction process stop; it does not simulate torn physical writes or prove arbitrary backup recovery safe.

Pure sender tests cover same-slot import permission with an existing session, reject different scopes and unresolved/reset gaps, and verify the guard performs no network activity. Native import/Keystore behavior remains source/compile only. Saving a rotated same-slot setup is not a new-session start or implicit Stop.

## Findings corrected or independently verified

During review the authors addressed omitted generation checks on prepared routes; incomplete loopback-origin exclusion; misleading restart-only grant activation wording; missing client validation of an issued epoch pin; expiration of a precreation ticket during an outage; conservative chosen-end caps during explicit recovery; consent loss during admission; and a foreground-start denial path that could revoke an existing session during Resume.

The private install command now performs an add-only merge preserving durable identity/epochs/bindings. Restart alone does not activate an externally generated grant file. The Java tests verify ticket/epoch persistence before POST, same-identity bounded refresh, no fallback to a fresh epoch after uncertain POST, and explicit user recovery after process recreation. The existing reset-in-flight Start guard was independently exercised with a controlled latch and passed; it was not a newly demonstrated defect.

System interruption and TLS/protocol/storage failures now suppress collection and preserve paused recovery without inventing an explicit Stop. The old 0.8 test expectations were intentionally updated to this new policy: known links can remain visible as paused, while no active sending consent or automatic revocation is asserted. Confirmed server terminal responses, explicit user Stop and the chosen end remain separate.

Known-ID Stop keeps the narrow session revoke capability. For an unknown prepared ID with an acknowledged ticket/epoch, the matching private grant enables an atomic own-slot reset. The sender no longer POSTs a new empty session solely to discover an ID before revoking. Without matching access it retains pending Stop and does not claim termination. If ticket and epoch were never acknowledged, the pre-POST persistence invariant proves no creation could have escaped and allows local cleanup without a reset.

Corrupt main-management recovery has a deliberately narrow fallback: after an explicit reset choice, separately valid prepared access can operate a temporary reset-only coordinator. Its store has no filesystem reference and refuses credential persistence. Source checks confirm it never replaces the main sender coordinator or overwrites/discards the unreadable journal. Confirmation applies to that prepared slot; it does not prove other unknown links ended. New Start/Resume remains blocked by the unreadable main journal. This boundary is checked with the actual pure helper and service source, not Android Keystore runtime.

## Android, recipient and network boundaries

Constructor restoration performs no HTTP and restores an unStopped journal as PAUSED, not active consent or pending Stop. Ordinary retry cannot resume it. Explicit Resume revalidates the same server/session, reconciles the durable sequence and selected end, and requires a fresh sample. Source contracts place provider subscription after reconciliation and deadline scheduling. System/foreground denial uses pause; user Stop/chosen end uses revocation. Generation invalidation, fix clearing and provider removal precede journal/network work. No native runtime was executed by these checks.

Local Stop/pause cannot recall an update already checked or dispatched. Transport releases the state lock before blocking network I/O so local controls can remain responsive. The Android HTTPS adapter has no cancellation handle; cancellation could not recall bytes already sent. The tests do not prove zero post-tap network events. After acknowledged remote Stop/reset, authorization/state is terminal for the old session/epoch and delayed requests cannot revive it. The point-erasure interval starts at the last accepted fresh update, which can have been in flight at the tap. Until Stop has no universal hard lifetime; an unconfirmed offline Stop can leave a paused server session open.

The recipient keeps last-known data only in tab RAM across transient failure/ordinary durable restart and labels its age, time, accuracy and uncertainty. A new tab cannot recover the old point from durable state. Clear, confirmed Stop/reset and known positive expiry wipe it. Earliest positive expiry cannot be extended by stale revalidation. Map navigation requires separate paged disclosure and final confirmation, with coordinates only and no session capability in the URL. There is no automatic geocoder/map request and no street address. Controller tests use a simulated DOM; no real browser or external Google request occurred.

## Remaining limitations that must stay visible

- **Complete snapshot rollback:** a complete old valid encrypted database and its manifest are accepted under the same retained key. The independent test deliberately demonstrates a current Stop becoming the older pre-Stop authorization state. It does not restore old coordinates, because none are persisted. Restoring the key file is unnecessary if the service still uses the original key; an attacker need not decrypt the snapshot. An independent rollback anchor is absent. Stale-backup disaster recovery needs an explicit policy that does not pretend old revocations remain intact.
- **Prior preparation:** sender access requires private operator provisioning, offline installation and import before use. No public anonymous enrollment exists. A person without prepared access cannot start a live session from public config. Finite reserved capacity, distribution/onboarding, operator availability, lost-installation administration, equitable first-use emergency access, costs and maintenance remain real decisions.
- **Compromise recovery operations:** local Forget and own-slot reset do not revoke a copied prepared capability. Offline disable/rotation now blocks the old token for admission/reset, but requires the operator, private key access and server downtime. Default recovery preserves existing session capabilities and links; ending them needs the explicit option. Enable alone reauthorizes the stored grant. Secure distribution of the new private bundle, incident decisions, operator responsiveness, maintenance availability and lost-installation administration are still required. A private file is not activation proof, and complete old snapshot restoration can undo administrative changes too.
- **Data and key operations:** wrong/missing keys, corruption or unavailable storage fail closed. No tested disaster-recovery, key escrow/rotation, backup consistency, measured capacity/SLO or multi-instance availability exists. Ciphertext hides control values, but file size, opaque record IDs/buckets/counts and timing can expose activity metadata. Retention/deletion is not physical erasure; filesystem snapshots, swap, core dumps, proxies, provider logs and backups were not configured or audited.
- **Location privacy:** the operator processes coordinates inside TLS; this is not end-to-end encryption or anonymity. Device activity may be monitored. Links, calls, clipboard/sharing and maps can leave traces. A recipient can copy data or forward bearer links; an offline Until Stop tab can retain last-known RAM until Clear or confirmed termination. Google receives coordinates/device/network metadata after explicit consent. Copies cannot be recalled and current location or recipient attention is never guaranteed.
- **Clocks and runtime:** device/server wall-clock agreement and exact OS wakeup are not established. There was no real Android Keystore/HTTPS/permission/hardware-location/foreground/notification/lock/Doze/Active-apps-Stop/process-death/OEM test, no real-browser rendering/accessibility/TalkBack/large-text/landscape test and no real sender-to-recipient field test. The default endpoint is blank; no operating public service or production infrastructure exists.

No remaining critical defect was demonstrated within the final executed cases and inspected source. This is a bounded independent review, not a comprehensive security certification, survivor-led safeguarding approval or guarantee of continuous tracking, concealment, rescue or delivery. The technical and runtime limits above remain substantive even after hosting is provided.
